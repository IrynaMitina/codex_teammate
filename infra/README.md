# AWS infrastructure

Deploy `ecr.yaml` once, then deploy `ecs-express.yaml` as **two separate
stacks**, with `Environment=staging` and `Environment=production`. Use the same
AWS account and region for the examples below, in a region supporting ECS
Express Mode and with at least two available availability zones.

Each environment owns a VPC, ECS cluster and Express service, private Single-AZ
PostgreSQL database, upload bucket, generated database/JWT secrets, IAM roles,
and a log group. AWS assigns unique physical names. VPCs have no peering; their
overlapping CIDRs are intentional. ECR is the only shared application resource.

Express Mode manages HTTPS ingress, load balancing, task security groups and
CPU scaling. Public task subnets avoid a NAT gateway; Express Mode assigns task
public IPs and restricts application ingress through its managed security
groups. The additional task security group grants no inbound access and serves
as the source identity for PostgreSQL access. Database subnets have no internet
route and the database is not publicly accessible. This follows the documented
[Express Mode networking behavior](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/express-service-work.html).

Defaults: 0.25 vCPU / 512 MiB per task, 1–2 staging tasks or 1–4 production
tasks, CPU target 60%, `db.t4g.micro`, 20 GiB encrypted gp3 storage, 1-day staging
or 7-day production database backups, and 7-day application logs. Override
`DatabaseInstanceClass`, `DatabaseStorageGiB`, or `LogRetentionDays` as needed.
Production starts with one task and Single-AZ RDS, as specified in the architecture;
it is not a highly available database deployment.

## Bootstrap and deploy

Use an AWS CLI profile with CloudFormation provisioning permissions, including
IAM role creation/passing and creation of ECS service-linked roles. These
commands create billable AWS resources. Run from the repository root.

```bash
aws cloudformation deploy \
  --template-file infra/ecr.yaml --stack-name drive-images

REPOSITORY_URI=$(aws cloudformation describe-stacks --stack-name drive-images \
  --query 'Stacks[0].Outputs[?OutputKey==`RepositoryUri`].OutputValue' --output text)
REGISTRY_HOST=${REPOSITORY_URI%%/*}
aws ecr get-login-password | docker login --username AWS --password-stdin "$REGISTRY_HOST"
IMAGE_TAG=$(git rev-parse HEAD)
docker build --platform linux/amd64 -t "$REPOSITORY_URI:$IMAGE_TAG" .
docker push "$REPOSITORY_URI:$IMAGE_TAG"
IMAGE_DIGEST=$(aws ecr describe-images --repository-name "${REPOSITORY_URI#*/}" \
  --image-ids "imageTag=$IMAGE_TAG" --query 'imageDetails[0].imageDigest' --output text)
IMAGE_URI="$REPOSITORY_URI@$IMAGE_DIGEST"

aws cloudformation deploy \
  --template-file infra/ecs-express.yaml --stack-name drive-staging \
  --capabilities CAPABILITY_IAM \
  --parameter-overrides Environment=staging ImageUri="$IMAGE_URI"
```

ECR must contain the image **before** creating the environment stack. Tags are
immutable; reuse the existing image if that commit was already pushed. Build
for `linux/amd64`, the default Express task architecture. Keep the resolved
`IMAGE_URI` as the release artifact; do not rebuild for production.

## Database migrations and release checks

The service uses `/docs` for liveness. This endpoint does **not** verify database
connectivity or schema readiness. A newly created stack is not ready for users
until migrations and authenticated API smoke tests succeed.

Run a one-off Fargate task with the task definition generated by the Express
service, overriding its primary container command to `["alembic", "upgrade",
"head"]`. Obtain the task definition ARN and container name using
`aws ecs describe-services` and `aws ecs describe-task-definition`. Use the
stack's `ClusterName`, `TaskSubnets`, and `TaskSecurityGroupId` outputs, with
`assignPublicIp=ENABLED`. The generated task definition supplies the same image,
roles, environment, secrets and log configuration. Wait for the migration task
to stop and require exit code zero; inspect the `LogGroupName` output on failure.
Do not run demo seeding in either deployed environment.

For an existing environment, register a revision of its task definition with
the candidate `IMAGE_URI`, run migrations with that revision, and require
success **before** updating the Express service through CloudFormation. Schema
changes must remain compatible with the currently running application during
the rollout. Initial stack creation necessarily starts the service before the
first migration; keep it out of use until the migration succeeds.

After staging migrations, smoke-test login, upload/download, sharing and
deletion through the stack's `Endpoint` output. Stop on failure. After manual
production approval, migrate production and deploy the exact tested digest:

```bash
aws cloudformation deploy \
  --template-file infra/ecs-express.yaml --stack-name drive-production \
  --capabilities CAPABILITY_IAM \
  --parameter-overrides Environment=production ImageUri="$IMAGE_URI"
```

Repeat the migration step for a first production deployment, then smoke-test.
These templates provision infrastructure; CI, smoke-test automation and the
manual approval gate belong to the separate CD pipeline described in the
architecture.

## Secrets and lifecycle

Only ECS's execution role reads this stack's secrets. The application task role
has object access only to this stack's bucket; no AWS keys are injected. Generated
database passwords omit punctuation because the application interpolates them
into its connection URL without escaping. Secrets are injected at task startup;
credential rotation must coordinate the RDS password and secret and restart
tasks. Automatic rotation is not configured.

Uploads, secrets and the shared repository are retained on stack deletion or
replacement. RDS is snapshotted on deletion/replacement, and production also has
deletion protection: explicitly disable it through a reviewed template change
before intentional teardown. Retained resources and snapshots require separate
cleanup and continue to incur charges. Never change an existing stack's
`Environment` value to repurpose it; use separate stacks.

## Validation

```bash
python -m pip install cfn-lint
cfn-lint infra/ecr.yaml infra/ecs-express.yaml
```

The template uses the native
[`AWS::ECS::ExpressGatewayService` resource](https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-ecs-expressgatewayservice.html).
Linting validates the template schema and references; a staging deployment is
still required to verify account permissions, regional capacity and runtime
connectivity.
